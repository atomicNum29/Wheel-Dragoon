# 전륜 독립 조향 및 4륜 구동

> 최신 RC 입력·가감속·임시 ±70° 보정은 [RC 조향 변경 문서](rc-steering.ko.md)를 따른다.
> 아래는 초기 구현 기록이다. 스키드 기본값·미검증 차단·±20° 임시 표·폴링 CAN 설명은
> 현재와 다르며, 현재는 독립 조향·사용자가 허용한 임시 보정·FIFO/ISR CAN을 사용한다.

구현 상태: 호스트 테스트를 수행하고 Teensy 3.2용으로 컴파일했습니다. 실제 주행, PWM, 서보 또는 CAN 타이밍에 대한 추가 검증은 수행하지 않았습니다. 저장소에 포함된 설정은 **양쪽** 조향 보정이 모두 검증될 때까지 의도적으로 구동을 차단합니다. 현재 선택된 모드는 스키드 조향입니다.

## 저장소 조사 및 유지된 아키텍처

`platformio.ini`는 Arduino/Teensy 환경에서 `src/main.cpp`를 선택합니다(`teensy32` 환경, Teensy 3.1/3.2용 `teensy31` 보드 ID). 이 프로젝트는 FlexCAN 라이브러리 대신 `src/flexcan0.cpp`에 구현된 자체 레지스터 수준 폴링 방식의 FlexCAN0를 사용합니다. 기존 조향 구현은 발견되지 않았습니다.

입력은 핀 0/1/2의 RC PWM 또는 Raspberry Pi에서 전달되는 바이너리 USB Serial 명령입니다. RC 모드 선택(STOP/MANUAL/AUTO/POWERDOWN)은 새 차량 운동학 모드와 별도로 유지됩니다. `main.cpp`의 기존 `DriveMode`는 RC 제어 권한을 뜻하며, `vehicle::DriveMode`는 스키드/독립 조향을 뜻합니다.

기존 11바이트 명령은 `AA 55 07 01 seq v_i16_le w_i16_le flags xor`로 유지됩니다. 단위는 milli-m/s 및 milli-rad/s이며, 비트 0은 활성화, 비트 1은 E-stop입니다. AUTO 타임아웃은 500 ms이고, 유효하지 않은 패킷은 이 시간을 갱신하지 않습니다. MANUAL은 RC 데드밴드/스케일링을 유지하고 수신기의 페일세이프에 의존하며, MCU에는 RC 신호 유실 타임아웃이 없습니다. 역기구학 계산은 계속 Teensy에서 수행합니다.

MD200T PID 207은 부호 있는 정수 RPM을 사용하는 두 폐루프 채널을 제어합니다. 출력이 비활성화되면 PID 174가 TQ-OFF를 전송합니다. 모터 텔레메트리는 PID **196/201**을 사용하며, 부호 있는 원시 RPM, 상태, 엔코더 카운트 및 MCU 수신 타임스탬프를 포함합니다. 전압 PID 143은 명시적 요청과 MID 7 응답을 사용합니다. 관련 파일, 전송 데이터 레이아웃, 텔레메트리 디코딩, 드라이버 설정 및 극성 규약은 유지됩니다.

| 드라이버 | CAN 명령 ID | CH1 | CH2 |
| --- | --- | --- | --- |
| A | 1 | FL | RR |
| B | 2 | FR | RL |

새로운 축 회전 방향 반전은 적용하지 않습니다. 양의 구름 RPM은 기존의 양의 채널 규약에 따라 전송됩니다. 조향을 활성화하여 주행하기 전에 저속에서 설치된 드라이버의 방향 설정을 확인하십시오.

`include/can_tx_schedule.hpp`와 `main.cpp`의 스케줄러는 기존 10 ms 주기를 유지합니다. 주기 시작 시 A를 전송하고, 실제 A 전송으로부터 최소 3 ms 후 B를 전송한 다음, B에 대한 3 ms 응답 구간 전체를 확보합니다. 응답이 일찍 도착해도 이 구간은 줄어들지 않습니다. 루프가 지연되면 놓친 주기는 건너뛰며 몰아서 전송하지 않습니다. 전압 요청은 100주기로 구성된 슈퍼프레임의 주기 0과 50에서 +6 ms 시점에 발생하여 각 드라이버가 초당 한 번씩 요청을 받습니다. 새로운 CAN 질의나 트랜잭션은 추가하지 않았습니다. 유일한 스케줄러 로직 변경은 A와 B 사이에 `motor_enabled`가 false가 되면 대기 중인 활성화된 B 명령을 취소하는 것입니다. 여기에는 조향 시작 단계의 구동 차단이나 호스트의 비활성화가 포함됩니다. 이 변경은 트랜잭션 타이밍을 바꾸지 않으면서 오래된 스냅샷으로 인한 안전상의 허점을 해소합니다.

기존 안전 처리 경로는 유지됩니다. 여기에는 호스트 타임아웃, 활성화/E-stop, RC STOP/POWERDOWN, CAN 송신 실패 및 드라이버 수신 타임아웃 보고/출력 차단, 드라이버 원시 오류, 저전압, 릴레이 시작 지연이 포함됩니다. 통신 타임아웃은 드라이버 자동 리셋을 유발하지 않습니다. 정상적으로 활성화된 영속도 명령은 PID 207과 감속을 사용하며, 비활성화/E-stop/타임아웃은 기존 PID 174 TQ-OFF 경로를 사용합니다. TQ-OFF는 **별도로 검증된 기계식 비상 브레이크가 아닙니다**.

### 확인된 문서 불일치 및 한계

- 기존 스키드 조향 혼합 계산은 새 실측 모델의 윤거 0.439 m가 아닌 **0.485 m**를 사용했습니다. 호환성을 위해 스키드 모드는 0.485 m를 유지하며, 독립 모드는 축거 0.420 m와 전륜/후륜 윤거 0.439 m를 사용합니다.
- 스케줄러 헤더는 이전에 자동 PID 196/201을 설명했지만, 브리지 주석과 일부 설명문은 PID 193/200을 설명합니다. 실제 제어는 196/201을 사용합니다. 브리지/벤치마크의 매칭 로직은 기존의 193/200 가정을 계속 사용합니다. 이번 리팩터링은 드라이버 응답 설정의 불일치를 해소하거나 어느 경로도 변경하지 않습니다.
- 워치독 진단에는 동작 중인 감지 소스가 없으며, 새 MCU 워치독도 추가하지 않았습니다. 기존 워치독을 검증했다고 주장하는 것은 부정확합니다.
- 펌웨어는 드라이버의 가속/감속을 설정하거나 호스트 측 RPM 변화율 제한을 구현하지 않았습니다. 드라이버 설정은 그대로 유지됩니다. 새 호스트 측 제한은 초기 시운전을 위한 추가 제약이며, 측정된 드라이버 동작을 의미하지 않습니다.
- CAN 수신 타임아웃과 오류에 따른 출력 차단은 기존의 상태 보고 10회 후 만료 정책을 따릅니다. 새로운 래치형 오류나 복구 핸드셰이크가 아닙니다. 전압 정보 노후화 및 수신 오버런 진단은 기존 동작을 유지합니다.
- 브리지/벤치마크 경로는 일반적인 모션 제약을 우회하는 원시 명령을 포함하여 기존 진단 동작을 유지합니다. 차량을 안전하게 고정한 상태에서 사용하십시오. 조향 준비 상태는 원시 CAN 브리지 명령을 제한하지 않습니다.

모든 펌웨어 상태는 고정 크기 저장 공간을 사용합니다. 새 패키지, 힙 할당, 블로킹 대기 또는 인터럽트 마스킹은 추가하지 않았습니다. PWM은 핀 9와 10에서 Teensy 코어의 `analogWriteFrequency`와 16비트 `analogWrite`를 사용합니다. 두 핀은 FTM0를 공유하며 **50 Hz**를 사용합니다(초기 시운전을 위해 가정한 값이며 설정 가능). FTM0 PWM 주파수를 변경하면 같은 타이머의 다른 PWM 채널에도 영향을 줍니다. 기존 릴레이 핀 5/6은 디지털 GPIO를 사용하고, RC 캡처는 에지 인터럽트를 사용합니다. 50 Hz에서 PWM 듀티의 시간 분해능은 약 0.305 마이크로초입니다. 실제 프레임/펄스 타이밍은 오실로스코프로 확인하십시오.

## 운동학 및 실행 가능성

기준점은 후륜 차축 중심입니다. +X는 전방, +Y는 좌측, +omega는 반시계 방향입니다. 전륜 위치가 `(x,y)`일 때 `(vx,vy)=(v-omega*y,omega*x)`입니다. `atan2(vy,vx)`를 계산하고 필요하면 부호 있는 구름 속도의 부호를 반전하여 ±90도 범위로 정규화한 뒤, 각 휠에 대해 개별 보정된 동작 범위를 검사합니다. 후륜 속도는 `v ± omega*rear_track/2`입니다. 실수 RPM은 `speed*60/(2*pi*0.065)`로 계산합니다.

이론적인 범위는 ±70도입니다. 실제 실행 가능 여부는 설정된 휠별 보정 한계 중 더 엄격한 범위로 결정합니다. 모터 회전 방향 반전이나 공통 비율 조정으로는 실행 불가능한 곡률을 해결할 수 없습니다. 실행 불가능한 명령은 모든 목표 RPM을 0으로 설정하고 생성된 조향각을 유지합니다. 기존 휠 명령은 호스트 측 제한기에 따라 감속합니다. 임의의 각도 클램프나 상위 수준 명령 보간은 사용하지 않습니다. 이 정책은 실행 불가능한 쐐기형 영역에 가까운 요청에서 차량을 정지시킬 수 있습니다. 가장 가까운 실행 가능한 경로, 보장된 제동 거리 또는 타이어 미끄러짐 보상을 제공하지는 않습니다. 향후 명령 투영 정책을 도입할 때는 순수 함수 `inverse()`를 교체하면 됩니다.

전륜 속도 벡터의 크기가 0.001 m/s 미만이면 해당 휠의 이전 생성 조향각을 유지하고 RPM을 0으로 설정합니다. 이는 의미 없는 `atan2(0,0)`과 정수 RPM 분해능 미만에서 발생하는 방향 노이즈를 방지합니다. 이론적인 분해능은 RPM당 약 0.006807 m/s입니다.

이론적인 ±70도 범위의 대표 결과는 다음과 같습니다(가속/전환 제한 적용 전).

| v | omega | FL 각도 | FR 각도 | 결과 |
| ---: | ---: | ---: | ---: | --- |
| 0.5 | 0 | 0° | 0° | 네 휠 모두 동일한 양의 RPM |
| -0.5 | 0 | 0° | 0° | 네 휠 모두 동일한 음의 RPM |
| 0.5 | 1 | ~56.26° | ~30.27° | 실행 가능한 좌회전, 휠별 속도는 서로 다름 |
| 0 | 1 | ~-62.41° | ~62.41° | 좌측 RPM은 음수, 우측은 양수; 전륜/후륜 속도 비율 ~2.159 |
| 0.2195 | 1 | 실행 불가능 | — | 명령 전체 거부 |
| 0 | 0 | 유지 | 유지 | RPM 0 |

임시 ±20도 설정은 후륜 차축 중심 회전을 포함하여 더 큰 각도가 필요한 회전을 의도적으로 거부합니다. 이러한 수치 사례는 실제 차량의 모터 축 회전 방향을 입증하지 않습니다.

## 모션 연동 제어

`MotionController`는 이전 생성 전륜 각도, 목표 전륜 각도, 현재 생성 전륜 각도를 추적합니다. `Transition`은 STARTUP, DRIVING, BRAKING, STEERING, SETTLING 상태를 제공합니다. 이 상태는 명령/추정 상태이며, 측정된 조향 위치를 뜻하지 않습니다.

무시할 수 없는 휠 회전 방향 반전이나 실행 불가능한 명령은 BRAKING을 유발하지만, 조향각 차이만으로는 감속하지 않습니다. 기존 5도 감속 조건과 설정값은 제거했습니다. 두 조향 명령은 공통 진행 비율을 적용하고, 더 많이 움직이는 쪽을 최대 180도/s로 제한하여 고정된 목표에 함께 도달합니다. BRAKING에서는 생성 RPM이 0이 되고 200 ms 정지 대기가 끝날 때까지 조향을 유지합니다. 시작/재활성화/모드 변경/반전 전환의 500 ms 안정화 단계는 남아 있으며, DRIVING 중 일반 조향 변경은 이 단계로 진입하지 않습니다. 이 동작은 명령 기준이며 실제 서보 도착 시각을 측정하지 않습니다.

각도 변화와 RPM 램핑은 부호 없는 밀리초 단위의 실제 경과 시간으로 제어합니다. 루프가 멈췄다가 재개된 경우 각 증분에 적용되는 경과 시간을 최대 50 ms로 제한하여, 지연을 한꺼번에 따라잡는 위험한 급변을 방지합니다. 안정화/시작 타이머는 전체 경과 시간을 사용하며 32비트 시간 카운터 순환에도 정상 동작합니다. RPM 목표 제한은 목표 비율을 유지하기 위해 하나의 공통 배율을 사용합니다. 가속/감속은 모든 휠의 변화율에 의해 제한되는 하나의 보간 비율을 사용하며, 휠별 부호가 갑자기 바뀌지 않습니다. 양자화는 최종 CAN 전송 경계에서만 최근접 정수 반올림과 유한값 검사로 수행하며, 디더링은 사용하지 않습니다.

기본값은 **200 RPM**, 가속 100 RPM/s, 감속 200 RPM/s입니다. 모터 제조사의 [인휠 모터 사양](https://www.mdrobot.co.kr/inwheel-motor)은 MDH100을 24 V, 400 RPM, 100–200 W로 명시합니다. 초기 시운전 제한인 200 RPM은 의도적으로 이 사양보다 낮게 설정한 값입니다. 제한을 높이기 전에 설치된 모델의 정격/최대 속도와 부하 상태에서 허용되는 가속도를 확인하십시오. 공개된 상한인 400 RPM을 초과하는 설정은 거부되며, 최종 변환에서도 이 상한을 적용합니다. MD200T의 일반적인 수치 범위를 모터 한계로 사용하지 않습니다. 호스트 비활성화, E-stop, 타임아웃 및 기존 드라이버 오류는 일반 램핑을 우회하여 생성 RPM 상태를 지우고, 기존 CAN 안전 경로를 통해 구동을 차단합니다.

명령 RPM이 0이라는 사실과 안정화 시간이 지났다는 사실은 모두 물리적 정지/완료에 대한 추정입니다. 실제 휠 감속이나 서보의 목표 위치 도달을 입증하지는 않습니다. 실제 부하가 걸린 차량에서 보수적인 대기 시간과 변화율을 확립해야 합니다. 시작 절차는 검증된 중립 펄스와 설정된 **1500 ms** 초기화 시간이 충분하다고 가정합니다. 측정된 최악의 시작 이동 시간을 기준으로 이 시간을 설정하십시오. 이 절차로 조향 준비 상태를 신뢰성 있게 확립할 수 없다면 보정을 미검증 상태로 두십시오. 그러면 구동은 계속 차단됩니다.

## 보정 및 모드 시운전

1. 차량을 안전하게 고정하거나 들어 올리고 구동 토크를 차단하십시오. 적절한 벤치 장비를 사용하여 각 서보의 안전한 PWM 프레임 주파수, 펄스 한계, 중립, 장착 방향 반전, 간섭 여유 및 실제 각도 응답을 개별적으로 확인하십시오. 펌웨어는 검증되지 않은 실제 조향 스윕 기능을 의도적으로 제공하지 않습니다.
2. `steering_config.hpp`의 `left_servo`와 `right_servo`를 각각 교체하십시오. 제공된 1500/1300/1700 마이크로초 값은 **비활성화된 임시 값**이며, RDS51150의 보정값이 아닙니다. 안전한 중립과 매핑을 측정한 뒤에만 `verified=true`로 설정하십시오. 둘 중 하나라도 false이면 서보 PWM을 출력하지 않으며 두 모드 모두에서 정상 구동을 차단합니다.
3. 테이블은 엄격한 오름차순의 액추에이터 각도/펄스 지점 3–5개로 구성되며, `neutral_us`에 해당하는 정확한 0도 지점을 포함합니다. 실제 장착 방향에 따른 반전은 테이블 조회 전에 적용합니다. 이를 통해 비선형 구간별 보간을 지원합니다. 실제 최소/최대 동작 각도는 테이블 범위 안에 있어야 합니다. 간섭 여유와 매핑을 검증한 뒤에만 초기 ±20도를 넘어 확장하십시오. 소프트웨어의 절대 한계는 ±70도로 유지됩니다.
4. PWM 타이밍, 시작 시 중립 위치로의 이동, 필요한 최소 안정화 시간, 방향 부호, 부하 상태의 제동/대기 및 작은 각도 변화 시 연동 동작을 검증하십시오. 드라이버 릴레이의 전원을 차단해도 서보 전원은 차단되지 않습니다. 전원 공급/GND 및 실제 서보 전원 상태는 계속 하드웨어에서 책임져야 합니다.
5. `MotionConfig::initial_mode`의 기본값은 `SKID_STEER`입니다. 보정 후에만 `INDEPENDENT_STEERING`으로 변경하십시오. 차량이 정지한 상태에서 다시 빌드하고 재부팅하십시오. 이 첫 버전은 **런타임 USB 모드 전환 패킷을 추가하지 않으며**, RC 제어 권한의 의미를 유지합니다.
6. 재사용 가능한 `request_mode(mode, standstill_confirmed)`는 시작 절차가 완료되고, 모든 생성 RPM이 0이며, 호출자가 실제 정지를 확인한 경우에만 변경을 허용합니다. 향후 호스트 통합에서는 true를 전달하기 전에 최신 휠 텔레메트리나 다른 신뢰할 수 있는 정지 확인 수단을 확보해야 합니다. 또한 스키드 모드로 주행하기 전에 영속도 명령을 적용하여 중립으로의 각도 변화 및 안정화를 거쳐야 합니다. 생성 RPM 추정값만으로 정지를 확인하지 마십시오.

## 진단 및 프로토콜 호환성

`0x01` 명령과 `0x82` System Status v2의 바이트 레이아웃 및 버전은 변경하지 않았습니다. 이전에 사용하지 않던 System Status 오류 비트는 이제 실시간 모션 진단을 제공합니다.

| 비트 | 의미 |
| ---: | --- |
| 12 | 마지막으로 평가한 활성화된 명령이 실행 불가능하거나 유효하지 않음 |
| 13 | 조향 시작/보정이 준비되지 않아 정상 구동이 차단됨 |
| 14 | 조향/구동 전환 상태가 DRIVING이 아님 |
| 15 | 마지막으로 평가한 목표에 RPM 제한에 따른 공통 배율이 적용됨 |

비트 12–15는 실시간 상태이며, 상태 보고 10회 동안 유지되는 과거 오류가 아닙니다. 거부된 명령은 활성화 상태에서 RPM 0을 목표로 감속하므로 MCU 상태가 ENABLED로 유지될 수 있습니다. ENABLED가 차량의 움직임을 뜻한다고 가정하지 말고 진단 정보를 확인하십시오. 비활성화 시에는 다음 활성화된 명령을 평가할 때까지 마지막 실행 가능성/제한 결과를 유지합니다. 기존 `0x81` 비트는 변경하지 않으며, 주기적 전송도 계속 비활성화되어 있습니다.

선택적 조향 상태 패킷 `0x83`은 기존 호스트 스트림 동작을 유지하기 위해 **기본적으로 비활성화**되어 있습니다. 호스트의 프레이밍 및 알 수 없는 유형 처리 동작을 확인한 후에만 `MotionConfig::publish_steering_status=true`로 설정하십시오. 활성화하면 기존 CAN 및 `0x82` 처리 후 초당 최대 두 번 전송을 시도합니다. USB 송신 공간이 부족하면 건너뛰며, 브리지 모드에서는 전송하지 않습니다. 호스트 수신기는 길이를 기준으로 프레임을 구분하고 알 수 없는 패킷 유형을 무시해야 합니다. 모든 프레임이 정확히 63바이트라고 가정하는 수신기는 배포 전에 수정해야 합니다.

| 바이트 | 필드 |
| --- | --- |
| 0–3 | `AA 55 0E 83` (총 18바이트) |
| 4 | 버전 = 1 |
| 5 | 차량 모드: 0 스키드, 1 독립 |
| 6 | 전환 상태: 0 시작, 1 주행, 2 제동, 3 조향, 4 안정화 |
| 7 | 플래그: 비트 0 준비 상태 추정, 비트 1 실행 가능, 비트 2 RPM 제한 적용 |
| 8–11 | uint32 LE MCU 시간(밀리초) |
| 12–13 | int16 LE FL 생성 조향각, 단위 0.01도 |
| 14–15 | int16 LE FR 생성 조향각, 단위 0.01도 |
| 16 | 예약 = 0 (피드백 없음) |
| 17 | 바이트 0–16의 XOR |

각도는 명확히 **명령값**이며 측정값이 아닙니다. 준비 상태와 전환 완료 여부는 서보 피드백 없이 산출한 추정값입니다.

## 검증

모든 C++ 호스트 테스트 하네스와 기존 Python 테스트를 실행합니다.

```bash
bash test/run_host_tests.sh
```

설치된 PlatformIO 환경에서 실제 타깃을 컴파일합니다.

```bash
pio run -e teensy32
```

호스트 테스트는 사례 A–H 및 J, 보정 거부/비선형/반전 매핑, 제한 및 반올림, 시간 카운터 순환, 모드 변경 보호 조건, E-stop/타임아웃 통합, 휠 채널 매핑, 그리고 사례 I에 해당하는 기존 CAN 트랜잭션 간격/상태/텔레메트리 회귀 테스트를 포함합니다. CAN의 전기적 동작, PWM 정확도, 서보 성능, 부하 상태의 제동, 타이어 끌림, 수신기 페일세이프 또는 추가 진단에 대한 ROS 호스트 처리는 검증하지 않습니다. 주행 전에 차량을 안전하게 고정한 상태에서 저속 하드웨어 테스트와 통신 모니터링을 반복하십시오.

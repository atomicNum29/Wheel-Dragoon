## 검토 결론과 근거 수준

검토 결과, “펌웨어는 문제가 없고 하드웨어 고장만 의심하면 된다”는 결론은 맞지 않는다. CAN 송신 취소 설정의 문서상 불일치, RC 입력 만료 미처리, 정지 전달 실패에 대한 대체 조치 부재가 확인된다. 다만 이 중 어느 것이 당시 사고를 유발했는지는 확인되지 않았다.

`확인`은 소스 또는 명시한 제조사 자료로 확인했다는 뜻이다. `추론`은 해당 조건에서 가능한 실행 경로이며 실기 재현 결과가 아니다. `미확인`은 당시 상태나 실제 장비 설정이 없는 부분이다. 아래 순서는 발생 확률 순위가 아니라, 사고 설명력과 코드 근거를 함께 고려한 조사 우선순위다.

## A. CAN 송신 취소 기능의 활성화 누락 — 가장 구체적인 코드 결함

현재 코드 근거: [flexcan0.cpp](../src/flexcan0.cpp)의 `abort_tx_mb()`, `can_begin()`, `can_transmit()`.

`abort_tx_mb()`는 TX mailbox가 inactive가 아니면 CODE=0b1001을 쓰고 IFLAG를 기다린다. 그러나 초기화에서 soft reset 후 `MCR[AEN]`을 설정하지 않는다. K20 문서는 abort 사용에 AEN=1을 요구하며, 해당 비트의 리셋값은 0이다. 따라서 이 복구 경로는 하드웨어 사용 조건과 불일치한다. [K20 Reference Manual, 44.3.2 및 44.4.6.1](https://www.pjrc.com/teensy/K20P64M72SF1RM.pdf#page=1098).

가능한 연결은 다음과 같다.

1. 정상 구동 중 한 TX가 ACK 상실, 버스 지연 등의 이유로 2 ms 안에 끝나지 않는다.
2. `can_transmit()`는 실패를 반환하지만 그 자리에서 pending TX를 정리하지 않는다.
3. 다음 명령에서 abort 경로를 사용하지만 활성화 조건이 빠져 있다.
4. 기대한 완료 플래그가 오지 않으면 새 명령을 mailbox에 넣기 전에 계속 실패할 수 있다. 기존 속도 명령이 늦게 송신되는 경우도 배제할 수 없다.
5. STOP도 같은 단일 TX mailbox를 사용하므로 전달이 막힐 수 있다. fault만으로 릴레이를 끄지는 않는다.

영구 실패의 정확한 레지스터 상태는 실기 미확인이다. “한 번 timeout이면 반드시 고착”이라고 단정하지 않는다. 그러나 AEN 누락 자체는 확인된 결함이며, 반복 실패가 생겨도 `can_begin()`을 다시 호출하는 운전 중 복구 경로가 없다. 부품 파손이 반드시 필요한 것은 아니고 일시적 통신 조건이 계기가 될 수 있다.

이 시나리오에서는 메인 루프와 RC 조향은 계속 살아 있을 수 있다. 따라서 실제 서보 명령까지 고정됐다는 관측이 있으면 이것만으로는 부족하다. 구별할 값은 `MCR[AEN]`, MB8 CODE/IFLAG, ESR1/ECR, TX 시작·완료·실패 횟수, 실제 PID174 송신이다.

## B. RC 신호가 없어져도 마지막 구동 명령을 계속 송신

현재 코드 근거: [rc_io.cpp](../src/rc_io.cpp)의 RC ISR·필터와 [control.cpp](../src/control.cpp)의 `update_drive()`.

세 채널 모두 마지막 유효 펄스 시각, 갱신 만료, 채널별 수신 건강 상태가 없다. MANUAL 경로는 `command_timeout=false`, `motor_enabled=true`를 설정하고 저장된 PWM을 계속 사용한다. `COMMAND_TIMEOUT_MS=500`은 RC 신호 유실을 막는 타이머가 아니다.

- 수신기 출력이 중단되면 마지막 속도·조향·MANUAL 모드가 남을 수 있다.
- 수신기가 Hold로 이전 PWM을 계속 내보내면 겉으로 정상 폭의 펄스가 유지된다. 이때는 펄스 만료 검출만 추가해도 송신기와의 링크 상실을 알 수 없다.
- 양쪽 조건 모두 MCU와 CAN이 정상이어도 이전 PID207을 계속 보낼 수 있다. 드라이버 통신 타임아웃도 신선한 명령이 계속 들어오므로 이를 막지 못한다.
- 모드 채널에 STOP 펄스가 도달하지 않으면 운전자가 스위치를 내려도 소프트웨어는 여전히 MANUAL이다.

물리 부품 고장이 반드시 필요한 것은 아니다. RF 링크 상실과 수신기의 정상적인 failsafe/Hold 설정만으로도 성립할 수 있다. 실제 수신기 모델·설정은 미확인이다. 구별하려면 MCU 핀에서 세 채널 PWM을 함께 확인해야 한다.

## C. MCU가 메인 루프로 돌아오지 않는 경우

현재 애플리케이션 근거: [main.cpp](../src/main.cpp)의 `setup()`/`loop()`, [serial_protocol.cpp](../src/serial_protocol.cpp)의 `receive_commands()`. 코어 근거는 2026-11-09에 확인한 `cores/teensy3/mk20dx128.c` 126–145, 672–680행의 당시 기록이다.

검토 당시 설치된 Teensy 3 코어의 기본 fault handler는 무한 루프에서 일부 USB/UART 처리를 호출하며 애플리케이션 `loop()`로 복귀하지 않는다. 기본 초기화는 watchdog을 비활성화한다. 현재 애플리케이션에도 watchdog을 활성화하거나 해당 fault handler를 교체하는 코드가 없으며, watchdog reset 원인 진단은 제공하지 않는다.

따라서 HardFault/BusFault 등이 생기면 RC 처리 결과를 CAN으로 전달하거나 릴레이를 변경할 메인 루프가 멈출 수 있다. 전원·타이머 클럭이 살아 있다면 하드웨어 PWM은 마지막 설정을 유지할 수 있고, 드라이버가 마지막 명령을 유지하면 구동도 이어질 수 있다. USB가 일부 응답한다는 사실만으로 메인 루프 생존을 입증할 수 없다.

다만 정상 입력만으로 그 예외를 발생시키는 특정 메모리 접근 결함은 찾지 못했다. 애플리케이션의 패킷 길이, 배열 인덱스, 고정 크기 루프를 검토했지만 재현 가능한 buffer overrun을 특정하지 못했다. 이 경로는 예외 발생 시의 결과가 확인된 것이며, 예외 발생 자체가 확인된 것은 아니다.

인터럽트 과다도 별도 후보다. RC는 CHANGE 인터럽트로 모든 에지를 처리하고, 애플리케이션 수준의 에지 빈도 제한은 없다. 입력선 부유·노이즈·수신기 이상으로 매우 많은 에지가 오면 메인 루프가 지연될 수 있다. CAN ISR도 한 번에는 6개만 처리하지만 계속 pending이면 다시 진입한다. 정상 100 Hz CAN 트래픽만으로 인터럽트가 포화된다는 근거는 없다. CAN 필터는 모든 standard data ID를 허용하므로 외부 트래픽도 부하가 된다.

설치 코어의 SysTick 우선순위는 32, CAN은 64, 기본 GPIO는 128이다. 따라서 “CAN ISR이 곧바로 SysTick을 막아 시간 자체가 정지한다”는 단순 설명은 맞지 않는다. 개별 ISR 횟수 제한과 전체 CPU 점유율 보장은 다르다.

결정적인 구별값은 메인 루프에서만 갱신하는 heartbeat다. ISR heartbeat나 정적인 LED, 계속 나오는 서보 PWM만으로는 메인 루프 생존을 증명하지 못한다.

## D. CAN·드라이버 장애를 감지해도 정지 전달이 보장되지 않음

현재 코드 근거: [control.cpp](../src/control.cpp)의 `update_power()`·`has_driver_fault()`·`update_drive()`, [can_control.cpp](../src/can_control.cpp)의 구동 명령·TX 실패 처리.

CAN TX 실패, 응답 timeout, driver status fault는 출력을 금지하고 PID174 TQ-OFF를 선택하게 한다. 그러나 전달 경로는 고장 난 동일 CAN이다. 이런 fault에서 GPIO 5/6을 LOW로 만드는 정책은 없다. 릴레이 출력은 RC POWERDOWN 여부만 따른다.

따라서 다음의 복합 조건이면 MCU는 FAULT를 표시하면서 차량은 계속 구동될 수 있다.

- CAN 배선/접지/트랜시버 또는 MCU TX 경로가 고장 나 정지 명령이 전달되지 않는다.
- 또는 드라이버의 통신 처리만 멈추고 내부 속도 제어는 마지막 명령을 유지한다.
- 드라이버 자체의 통신 단절 자동 정지가 없거나 비활성/부적절한 설정이다.

드라이버가 마지막 속도를 실제로 유지하는지, 자동 정지가 어떤 설정인지 이 저장소로는 확인할 수 없다. 펌웨어는 그 설정을 읽거나 보장하지 않는다. 단순히 드라이버 전원이 완전히 꺼졌다는 조건만으로 토크를 유지한 정속 주행을 설명할 수는 없다.

MCU의 CAN 초기화 성공 플래그는 운전 중 bus health가 아니다. ESR1/ECR를 읽는 경로도 없다. 다만 CTRL1 값의 BOFFREC=0은 하드웨어 자동 bus-off 복구를 허용한다. “펌웨어 재초기화 코드가 없다”와 “CAN 하드웨어 자동 복구도 없다”는 구분해야 한다. [K20 Reference Manual, 44.3.3](https://www.pjrc.com/teensy/K20P64M72SF1RM.pdf#page=1055).

## E. 모든 명령 사이에 3 ms가 보장되는 것은 아님

현재 코드 근거: [can_control.cpp](../src/can_control.cpp)의 `transmit_if_due()`와 [can_tx_schedule.hpp](../include/can_tx_schedule.hpp).

A→B 및 B→전압 조회는 실제 명령 시작부터 3 ms를 확인한다. 그러나 전압 조회 시각은 저장하지 않으며, 다음 cycle의 A는 그 조회와의 간격을 검사하지 않는다.

코드에서 허용되는 예시이며 측정/테스트 결과는 아니다.

| cycle 기준 시각 | 동작 |
|---:|---|
| 0 ms | Driver A 명령 |
| 6.5 ms | 루프 지연 뒤 Driver B 명령 |
| 9.5 ms | B의 3 ms 창 이후 예정된 전압 조회 |
| 10 ms 이후 | 다음 cycle Driver A 명령 가능 |

전압 조회가 있는 cycle에서 두 마지막 송신 시작 간격은 약 0.5 ms가 될 수 있다. 이것이 CAN 프로토콜 위반이라는 뜻은 아니지만, 드라이버 처리 간격을 보장하려는 의도는 충족하지 못한다. 3 ms 창 자체도 버스의 마지막 응답 이후 3 ms 무통신을 뜻하지 않는다.

MDROBOT 게시판에는 MD200T가 짧은 명령 간격에서 통신 무응답이 되었고 간격 확보 후 해소되었다는 사용자 보고와 제조사 답변이 있다. 이는 드라이버 상호작용을 조사할 근거이며, 이번 사고의 독립 검증이나 모든 드라이버에 대한 최소 간격 사양은 아니다. [제조사 Q&A](https://www.mdrobot.co.kr/QA/?bmode=view&category=25130028q7&idx=174115794&q=YToxOntzOjEyOiJrZXl3b3JkX3R5cGUiO3M6MzoiYWxsIjt9&t=board).

또한 루프가 반복적으로 10 ms보다 느리면 cycle 이월 때 이전 B 예약을 버리고 새 A부터 시작할 수 있다. 유한한 일회 지연을 처리하는 설계이지만, 지속 지연에서는 B의 서비스가 계속 밀릴 수 있다. 이 역시 정상 루프에서 실제 발생했다는 증거는 없다.

## F. STOP 처리와 물리적 제동은 다름

현재 코드 근거: [rc_io.cpp](../src/rc_io.cpp)의 모드 필터, [control.cpp](../src/control.cpp)의 `update_drive()`, [md200t_can.cpp](../src/md200t_can.cpp)의 `md200t_torque_off()`.

RC STOP은 PID174 TQ-OFF다. 별도의 속도 0 유지·전자브레이크 제어 명령을 보내는 구현이 아니다. 제조사도 PID174를 servo lock 해제에 사용하는 것으로 안내한다. 따라서 경사와 관성이 있으면 STOP을 수신해도 차량이 계속 움직이는 경우를 고려해야 한다. [MDROBOT PID24/PID174 안내](https://www.mdrobot.co.kr/QA/?bmode=view&idx=14120932).

당시 “같은 속도”는 계측되지 않은 관측이다. 실제 모터 전류/토크와 RPM으로 정속 구동이 확인되면 단순 관성·자유회전 설명은 약해진다. 서보 고착과 TQ-OFF 후 경사 이동이 함께 생기는 복합 시나리오도 가능하지만 입증되지 않았다.

모드에는 10개 유효 펄스 평균이 적용된다. 1500→1200 us로 바뀌면 평균이 STOP 기준인 1300 us 미만이 되기까지 7개의 새 표본이 필요하다. 수신기가 50 Hz라는 가정에서는 약 0.14초 규모이며, 이후 CAN 스케줄 지연도 붙는다. 지속 무응답의 설명은 아니지만 충돌 직전 STOP의 효과를 해석할 때 중요하다. 수신기 실제 주기는 미확인이다.

## G. RC 무효값이 안전 정지 대신 극단 명령 또는 이전 명령이 됨

현재 코드 근거: [rc_io.cpp](../src/rc_io.cpp)의 속도·조향 ISR 및 `offset_with_deadband()`, [control.cpp](../src/control.cpp)의 RC 변환.

- 전후/조향 ISR은 폭의 상한 2000 us만 검사한다. 지나치게 짧은 펄스도 평균에 들어간다.
- 변환 함수는 범위 밖 값을 fault로 처리하지 않고 1000–2000 us로 clamp한다. 작은 값은 중립이 아니라 음의 최대 입력 쪽으로 간다.
- `v_pulseWidth`와 `w_pulseWidth`의 초기값은 0이다. 모드만 MANUAL이 되고 전후 채널이 한 번도 유효하게 갱신되지 않으면 0을 1000 us로 바꾸어 음의 속도를 요청할 수 있다. 모션 시작 절차는 있지만 채널 유효성 게이트는 없다.
- 반대로 2000 us보다 긴 전후 펄스는 버려져 이전 값이 남는다. 모드 펄스도 800–2200 us를 벗어나면 이전 모드를 유지한다.
- RC 폭 계산은 에지 캡처 하드웨어 시각이 아니라 ISR 실행 시점의 `micros()`다. 인터럽트 지연으로 폭이 왜곡될 수 있으나 정상 CAN 부하가 이를 심각하게 만든다는 증거는 없다.
- 극단적으로 상승 에지 후 약 35.8분 이상 지난 뒤 하강 에지가 오는 비정상 입력에서는 전후 ISR의 signed `long tmp`와 하한 검사 부재도 문제가 될 수 있다. 정상적인 짧은 PWM에서의 71.6분 래핑 문제와는 다르며, 장시간 고정된 신호 등 추가 조건이 필요하다.

전후/조향 채널만의 이상이면 정상 모드 채널의 STOP 경로는 남는다. 전체 조종 상실을 설명하려면 모드도 멈추거나 다른 고장이 동반되어야 한다.

## H. USB 전송 성공 횟수가 구동 fault의 수명을 결정함

현재 코드 근거: [control.cpp](../src/control.cpp)의 `report()`·`consume_error_reports()`·`has_driver_fault()`, [serial_protocol.cpp](../src/serial_protocol.cpp)의 `send_system_status()`.

CAN 오류·드라이버 오류·저전압의 동일 카운터를 상태 보고와 출력 차단에 사용한다. 카운터는 `Serial.write()`로 0x82 패킷을 전달한 횟수에 따라 감소한다.

- USB 전송이 계속 막히면 일시 오류도 오래 남아 주행이 다시 허용되지 않을 수 있다.
- USB 전송이 가능하고 오류가 더 이상 갱신되지 않으면 10회 후 fault 게이트가 풀린다. MANUAL과 비중립 입력이 유지되면 모션 재활성화 절차를 거쳐 다시 구동할 수 있다. 별도 수동 재허가/중립 확인은 없다.
- 전원 복귀·CONTROL 세션 재진입도 오류 기록을 초기화한다.

이것은 정지 지속과 재출발 문제이며, 단독으로 STOP 무시한 지속 구동을 설명하지 않는다. USB 버퍼에 쓰기 성공한 것은 호스트가 로그를 읽어 저장했다는 뜻도 아니다.

## I. BRIDGE/USB 경로의 제어 우선순위

현재 코드 근거: [control.cpp](../src/control.cpp)의 `enter_bridge_mode()`·`update_drive()`, [can_debug.cpp](../src/can_debug.cpp)의 요청 처리, [serial_protocol.cpp](../src/serial_protocol.cpp)의 `receive_commands()`. 이 항목의 BRIDGE 경로는 디버그 프로필에만 포함된다.

유효한 bridge/benchmark 패킷은 RC MANUAL에서도 BRIDGE로 진입할 수 있다. 최초 진입 시 TQ-OFF를 한 번 시도하지만, 이후 raw PID207을 전송할 수 있다. BRIDGE에서는 RC STOP에 따른 주기적 PID174가 나가지 않는다. benchmark의 반복·종료에도 별도 구동 정지 보장이 없다. RC POWERDOWN은 메인 루프가 정상이라면 별도로 릴레이를 제어한다.

또한 MANUAL은 USB command의 estop 플래그를 채택하지 않고 `estop_active=false`로 둔다. 따라서 `control.py --estop`을 MANUAL의 비상정지로 믿으면 안 된다. 이것은 현재 RC 전용 정책의 실제 동작이며 당시 RC 3채널 STOP과는 별개다.

`protocol::receive_commands()`는 바이트/시간 예산 없이 수신 버퍼가 빌 때까지 처리한다. 호스트가 지속적으로 유효 bridge 명령을 보내면 한 명령당 최대 100 ms RX 대기가 누적되어 메인 루프와 POWERDOWN 처리를 지연시킬 수 있다. 단순 잡음 바이트만으로 CPU가 반드시 포화된다는 뜻은 아니다.

이전 보고에서는 Pi 시리얼 프로그램이 실행되지 않았으므로, 당시 사고의 우선 후보로 높게 두지 않는다. 다만 펌웨어만으로 가능한 별도 제어 상실 경로다. 유효 패킷 유입 없이 BRIDGE가 저절로 된다고 주장할 근거는 없다.

## J. 전원·서보·기구·배선의 복합 장애

다음은 소스에서 검출·차단하지 못하는 조건에 대한 가설이며 실측되지 않았다.

- 서보 고착, 링크 풀림/파손, 타이어 걸림: 실제 조향 피드백이 없으므로 명령각이 도달하면 제어기는 도달했다고 간주한다. 그러나 이것만으로 정상 RC STOP/CAN 정지가 무효가 되지는 않는다.
- 서보 부하 증가나 접지 변동이 수신기/MCU/트랜시버 전원에 영향을 주는 구성: B/C/D가 동시에 생길 수 있다. 공유 전원 여부, 전류 여유, 실제 전압 강하가 미확인이다.
- 릴레이 접점·배선·논리 극성 오류: GPIO가 바뀌어도 실제 PWR_SW가 열리지 않을 수 있다. 펌웨어의 POWERDOWN 상태는 실제 접점/전원 차단 확인이 아니다.
- 드라이버 PWR_SW는 제조사 자료상 제어전원 ON/OFF 입력이며, MCU GPIO 명령을 배터리 주전원 물리 분리와 동일시할 수 없다. [MDT Series 제조사 자료](https://www.mdrobot.co.kr/244).
- 홀/엔코더/모터 배선·드라이버 과열 등: 모터 상태 이상을 만들 수 있지만 CAN과 MCU가 정상이라면 fault→TQ-OFF 경로가 남는다. STOP까지 실패했다고 설명하려면 정지 전달 실패 또는 토크 오프 후 이동을 추가로 확인해야 한다.

전압 감시는 각 드라이버의 PID143을 1 Hz로 읽는다. MCU 3.3 V·수신기·서보 전압을 직접 측정하지 않으며 순간 강하를 보장해서 잡지 못한다. 저전압 판정은 양쪽 전압 모두 유효할 때만 한다. 한쪽 전압이 stale이면 다른 쪽의 낮은 전압만으로 새 저전압 fault를 만들지 못한다. `voltage_stale` 자체는 진단용이며 구동 차단에 포함되지 않는다.

## K. 검토했지만 현재 사고 원인으로 특정하지 못한 항목

- 일반적인 `micros()`/`millis()` 래핑: CAN 창·송신 주기·모션 타이머는 unsigned 차이를 사용한다. 정상 서비스 간격에서 래핑만으로 지속 정지하는 경로는 미발견이다. `prevTime==0` 경계 누락, 긴 비정상 PWM의 signed 변환은 별도다.
- CAN 응답 없음에 의한 단순 무한 대기: 레지스터 대기는 시간 제한이 있다. A의 반복 송신 실패와 C의 실행 정체는 따로 봐야 한다.
- RX FIFO/queue: 단일 생산자/소비자, 32칸 마스크, unsigned head-tail 차이를 사용한다. 포화 시 새 프레임을 버리며 배열 밖에 쓰는 구현은 아니다. 한 ISR과 메인 drain의 개수는 제한되어 있다. 이 사실만으로 IRQ 지연·실제 하드웨어 동작까지 검증된 것은 아니다.
- 패킷 배열: 허용 길이가 고정되고 최대 28바이트다. telemetry와 benchmark 출력 offset은 배열 크기 내다. 정상 경로의 명백한 범위 초과 쓰기는 찾지 못했다.
- 모션 계산: 비유한 값·실행 불가능 명령을 거부하고 RPM을 제한한다. STEERING/SETTLING 지터는 출발을 막을 수 있지만 정상 모드 STOP 처리를 우회하지 않는다.
- USB TX: 애플리케이션은 공간을 확인한다. 설치 코어도 대기에 유한한 카운트 제한이 있어 단순 미수신만으로 영구 hang이라고 단정할 수 없다. 다만 코어에 availableForWrite 이후 autoflush 경쟁 가능성이 주석으로 남아 있어 모든 호출이 항상 즉시 반환한다고 보증할 수도 없다.
- 진단 수치: cycle/count 래핑은 진단값을 왜곡할 수 있지만 기본 환경에서는 타이밍 프로파일이 꺼져 있고, 해당 카운터는 구동 제어 판단에 쓰이지 않는다.
- CAN 수신 경로의 설명과 관측 한계는 [CAN 구조](can-rx-fifo.md)를 따른다. 구조 설명 자체는 사고 원인의 증거가 아니다.

## FAULT 표시가 없더라도 안전하다고 볼 수 없는 이유

| 조건 | 현재 MCU 판정/동작 |
|---|---|
| RC 펄스 유실 또는 수신기 Hold | 직접 fault 검출 없음. MANUAL과 이전 명령이 유지될 수 있음 |
| CAN TX 실패 / 3 ms 응답 누락 / status 비영 | fault 및 같은 CAN을 통한 TQ-OFF 선택 |
| CAN RX overrun | 진단 표시. 응답 누락 등이 동반되어야 별도 구동 fault가 걸림 |
| 전압 stale | 진단 표시. 그 비트만으로 구동 차단하지 않음 |
| 실제 서보 미도달 / 링크 고장 | 직접 검출 없음 |
| MCU 예외 | 정상 상태 보고와 정지 로직 자체가 실행되지 않을 수 있음 |
| GPIO POWERDOWN 출력 | 접점·실제 전원 차단 확인 없음 |

`MOTOR_STATE_FAULT`는 소프트웨어 상태이고 물리적 정지를 확인한 상태가 아니다. 반대로 실제 조종 상실이 MCU의 fault 비트 없이도 가능하다.

## 후속 확인에서 필요한 증거 — 실행하지 않은 항목

| 분기 질문 | 필요한 관측 | 구분되는 후보 |
|---|---|---|
| STOP 입력이 MCU 핀까지 왔는가? | 전후·조향·모드 PWM 동시 기록 | B/G 대 C/D |
| 메인 루프가 계속 돌았는가? | 메인 루프 전용 heartbeat, 마지막 실행 단계 | C 대 A/B/D |
| MCU가 어떤 CAN 명령을 실제 보냈는가? | 외부 CAN 기록, PID207/174, A/B 구별 | B/I의 계속 구동 명령 대 A/C의 송신 중단 |
| TX가 왜 실패했는가? | MCR AEN, MB8 CODE/IFLAG, ESR1/ECR | A와 물리 버스 장애 |
| 드라이버가 정지 명령을 수용했는가? | 응답·RPM·전류·드라이버 LED | D 대 F |
| 전원/릴레이가 실제 바뀌었는가? | MCU/수신기/서보 전압과 GPIO/접점 동시 기록 | 공통 전원 및 실제 POWERDOWN 실패 |
| 드라이버 명령 간격이 좁아졌는가? | PID143→다음 명령 및 모든 TX 간격 | E |

아직 없는 하드웨어 정보: 조종기·수신기 모델 및 채널별 failsafe 설정, MD200T 펌웨어/통신 단절 처리 설정, 전원·접지 연결도, 릴레이 접점 배선, 실제 제동장치 유무, 사고 당시 바이너리 식별값.

수정 검토의 첫 대상은 A의 CAN abort 경로, B/G의 RC 유효성, D의 정지 전달 실패 대응, H의 fault 상태와 USB 보고 분리다. 구체적인 차단·재허가 정책은 사용자와 정해야 한다. 독립 정지 수단이 없는 상태의 자유 주행 재현은 이 검토에 포함하지 않으며, 이후 시험을 하더라도 별도 지시와 구동 에너지 격리 조건이 필요하다.
